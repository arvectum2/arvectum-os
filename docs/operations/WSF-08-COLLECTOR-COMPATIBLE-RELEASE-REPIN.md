## Timing review — candidate operational improvement (2026-11-19)

The existing 0.6.2 contract uses fixed UTC three-hour ledger windows, a single relative StartInterval=10800 schedule with RunAtLoad, and four-hour observation freshness. The successful re-pin retains the prior verified window. Relative launchd reload late in that same window may return not-due and defer the next eligible scan until the new interval crosses the freshness limit. This is a possible truthful stale interval; do not suppress freshness warnings or reset the ledger/status to create a duplicate.

Before the next approved change, estimate the restart time against the most recent actual per-source checked_at and next UTC due window. Prefer a maintenance window shortly after a successful due scan, allowing enough time for verified backup and exact re-pin, so the next relative interval should remain within the four-hour freshness budget. Alternatively a reviewed restart in the next eligible window can run a due scan immediately. Do not change the contract's cadence, broaden source scope, create additional daemons, manipulate clock/status or start an unapproved job. Actual next-run time cannot be guaranteed by an estimated phase, particularly during sleep, retries or outage. If a phase gap is likely, disclose it and obtain a bounded operational decision rather than silently treating saved data as fresh. After restart verify attribution, nonduplication and the next actual interval; preserve failure evidence. This proposal is not authority to alter the existing job or initiate a new maintenance window.
